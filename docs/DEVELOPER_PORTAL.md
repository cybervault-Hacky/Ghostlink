# GhostLink Developer Portal (Phase 10B)

The Developer Portal is a secure web application for GhostLink developers:
remote developer accounts, developer credentials with a full lifecycle
(create / rotate / revoke / verify), projects, sessions/devices, security
activity, and account settings.

> **Status: Phase 10B foundation.** This is a real, tested, security-focused
> portal — not a mock. It is **local-first** and can be run entirely on a
> development machine. A live internet deployment (HTTPS, real email, full
> WebAuthn attestation breadth) requires the production configuration
> documented in [docs/DEPLOYMENT.md](DEPLOYMENT.md).

## 1. Principles

* **Minimal, auditable dependencies.** The backend is a WSGI application
  built on the Python standard library plus the already-present
  `cryptography` library. SQLite is the development database; the schema is
  PostgreSQL-ready.
* **Secrets are never stored in plaintext.** Passwords are PBKDF2-hashed;
  developer secrets, recovery codes, session/token values are stored only as
  salted verifiers/hashes. Plaintext is shown exactly once, if ever.
* **Fail closed.** Everything is validated, authorized, rate-limited, and
  audited. Malformed or unauthorized requests never leak sensitive state.
* **No telemetry, no analytics, no tracking.** Security activity is
  application functionality, not advertising.

## 2. Architecture

```
portal/backend/portal_server/
  app.py         WSGI app, router, and all API handlers
  auth.py        PBKDF2 password hashing, sessions, tokens, CSRF
  db.py          SQLite schema (PostgreSQL-ready model)
  http.py        minimal WSGI request/response helpers + security headers
  mfa.py         TOTP (RFC 6238)
  webauthn.py    WebAuthn/passkey ES256 verification
  security.py    rate limiting, security headers
  __main__.py    dev server entry
portal/web/      React + TypeScript + Vite frontend
```

The frontend never stores secrets in persistent state; a credential secret
is a transient local variable shown once and then discarded. API calls are
same-origin (proxied in dev), so cookies stay HttpOnly and the JS only holds
a per-session CSRF token.

## 3. Authentication model

* **Sign-up** creates a `pending` account and mints a single-use,
  short-lived email-verification token (stored hashed). Email delivery uses
  a configurable provider; a **dev adapter** records messages for local
  testing (never claimed as real delivery unless a provider is configured).
* **Sign-in** verifies the PBKDF2 hash, issues an HttpOnly `SameSite=Lax`
  session cookie plus a per-session CSRF token, and rotates failures into an
  account lock/rate limit.
* **MFA (TOTP)** — RFC 6238 with a server-side base32 secret. When enabled,
  sign-in requires a one-time code; recovery codes are generated by CSPRNG,
  shown once, stored hashed.
* **WebAuthn / passkeys** — the server issues a challenge and verifies an
  ES256 (P-256) assertion signature with `cryptography`. No biometric data is
  ever collected, transmitted, or stored: the browser handles device
  authentication and the server receives only cryptographic assertions.
* **Password reset** uses single-use, short-lived, hashed tokens with generic
  (email-existence-hiding) responses.

## 4. Developer credential lifecycle

* **Create** — a new `gl_dev_…` credential is generated with the Phase 10A
  CSPRNG key generator; the secret is shown **once**, then only salted
  verification material is stored (reusing `ghostlink.developer.keys`).
* **List / metadata** — `key_id`, name, status, created/last-used/rotation
  timestamps. The secret is never returned.
* **Rotate** — requires confirmation; the old credential is revoked
  immediately and a new one is shown once.
* **Revoke** — requires confirmation; persistent and irreversible (a revoked
  key can never authenticate again).
* **Verify** — a public endpoint checks a presented credential with constant-
  time comparison and returns a generic 401 for unknown/revoked/wrong keys
  (no existence leak).

The portal's credentials are **remote API credentials** distinct from the
local Phase 10A credentials. Phase 10B does **not** require pasting your
permanent local secret into the website; credentials are created in the
portal and managed independently. A secure enrollment protocol between a
local GhostLink install and the portal is a documented future extension
(short-lived, single-use, revocable, auditable enrollment tokens) — not yet
implemented.

## 5. Sessions & security activity

* Sessions are revocable individually or "sign out all others".
* A metadata-only audit trail records sign-in, failed sign-in, key
  created/rotated/revoked, password change, MFA enable/disable, and passkey
  registration. No password, key, token, or session value is ever logged.

## 6. API

Versioned under `/api/v1/`. See [docs/API.md](API.md) for the full reference.

## 7. Security controls

* Rate limiting (IP and account scoped) for sign-in, sign-up, password
  reset, email verify, MFA, credential create/rotate/revoke, and session
  actions.
* CSRF protection on all unsafe methods via a per-session token header.
* Security headers (CSP, `X-Content-Type-Options`, `Referrer-Policy`,
  `X-Frame-Options`, `Permissions-Policy`); HSTS in production.
* Session cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` in production.

## 8. Known limitations (honest)

* Email delivery is **not** wired to a real provider by default; a dev
  adapter records messages locally. Production requires `EMAIL_PROVIDER`.
* WebAuthn supports the standard **ES256 / P-256** credential format and
  verifies assertion signatures itself. Deployments that must accept every
  credential/attestation format should plug in a maintained WebAuthn library
  (see [DEPLOYMENT.md](DEPLOYMENT.md)); the interface is the extension point.
* The portal is served by a WSGI dev server for local use; production needs a
  real WSGI server + HTTPS reverse proxy.
* The database uses SQLite in development; PostgreSQL requires the schema
  (identical) plus a Postgres driver — the schema is PostgreSQL-ready but a
  Postgres backend is not yet shipped.

## 9. What the portal is NOT

* No marketplace, payments, subscriptions, or billing.
* No team/org system, social features, or analytics platform.
* No biometric data collection or fake biometric verification.
* No permanent local-secret capture via web forms.
